# Treat each box as a parcel, not a component

Eloi does not need a UI framework. It needs one host that controls the frame, plus a small contract that each box runtime signs. Across Svelte 5, Solid, Vue Vapor, Astro, Lit, single-spa, R3F, MapLibre, regl, Flutter and Taffy, the parts that hold up are the same few mechanisms. The compiler decides *where* each value goes, and runtime signals decide *when*. Each mounted unit gets an owner that disposes everything it created. The parent controls position and width, and content reports only height. The host owns size, visibility and the frame clock, and pushes them to guests that ask for frames instead of running their own loops. Every one of these fits the existing design docs: the four stages, the `mount()`/`FrameHandle` host contract, the rule that "width flows down, height flows up", and `<frame-elevation>` with light-DOM `data-slot` openings. What is missing is the reverse contract: what the frame promises to the box, and what the box promises back. For the portfolio, that contract can be small: a static-HTML box with no JavaScript, plus a DOM runtime box with `mount(el, ctx)`, an `AbortSignal`, pushed size and visibility signals, per-box error isolation and stable ids. GPU concerns (device-pixel sizing, context loss, clock inversion, `always`/`demand`/`never` loop modes) are well understood from R3F, MapLibre and regl. They should have reserved names in the contract now and be built when the city game or isidex needs them. Most of the risk is scope creep, and the research names which traps to avoid: async-in-the-graph, Module Federation, resumability, shared canvases and time-sliced schedulers.

## Compiler-first frameworks compile placement and leave dependencies to runtime

Svelte 5, Solid's JSX compiler and Vue Vapor all split the work the same way. At build time the compiler emits a static HTML template that is cloned per instance, the paths to the dynamic nodes, and which expression feeds which DOM setter. At runtime, dependency tracking, propagation, scheduling and cleanup take over. In Svelte 5 output, a binding becomes a `template_effect` that calls ``$.set_text(text, `Hello ${$.get(name)}`)``, so **only that text node is touched when `name` changes, and the component never re-renders** ([Svelte playground](https://svelte.dev/playground/761a0a6cc2834afb842942e1d23875b1)). Vapor's output has the same shape, a `renderEffect(() => setText(n0, …))` per binding ([Vue Mastery](https://vuemastery.com/blog/the-future-of-vue-vapor-mode)). The more instructive story is what Svelte stopped doing. Svelte 3/4 inferred dependencies lexically at compile time, and that broke under refactoring, so **Svelte 5 moved dependency discovery back to runtime** while keeping structural compilation ([Svelte blog: runes](https://svelte.dev/blog/runes)). The same post notes that Svelte's SSR output drops signals entirely. This is the "compile what you can" principle taken to its limit: zero reactive runtime for content proven not to change.

The mapping onto Eloi's stages (system.md §5) is close. Design-stage values compile to constants, CSS and static SVG. Load-stage values are one-shot initialisation with no signals allocated. Only layout- and moment-stage values become signals. That is Svelte's SSR trick applied by stage instead of by environment, and it is how system.md §6.5's "a static frame ships zero runtime JavaScript" turns into something enforceable. The lesson for the compiler is to never let it infer reactive dependencies. It should infer *stages* (which system.md already does, as a type) and *sinks*: which CSS custom property, attribute or uniform a value writes to. Runtime signals then handle propagation.

For that runtime graph, `@preact/signals-core`, which the design docs already chose, is the right call and should not be reimplemented. It is push-pull. A write pushes only a dirty notification. A computed then checks its sources' version numbers in order and recomputes only if one changed, and an equal result does not bump its own version, which cuts off downstream work. Dependencies are doubly linked lists of edge nodes that are reused across runs, so **steady-state reruns allocate nothing**. Unobserved computeds unsubscribe on their own, so they need no manual disposal ([Preact: Signal Boosting](https://preactjs.com/blog/signal-boosting/)). The `watched`/`unwatched` options ([signals-core README](https://raw.githubusercontent.com/preactjs/signals/main/packages/core/README.md)) are what an Eloi box needs to start a ResizeObserver or IntersectionObserver only while someone is listening. The TC39 Signals proposal is still Stage 1, with only a polyfill that its own README calls unstable ([tc39/proposal-signals](https://github.com/tc39/proposal-signals)). Do not build on its API yet. Do copy its *shape*: `notify` is synchronous and may not read signals, and the framework flushes later. In Eloi, that becomes "an effect marks a box dirty and requests one frame". It does not draw.

Signals-core lacks one thing Solid has: an owner tree. Solid's `createRoot(fn)` returns a `dispose` that unlinks every computation from its sources, disposes owned children and runs their cleanups ([solid signal.ts](https://raw.githubusercontent.com/solidjs/solid/main/packages/solid/src/reactive/signal.ts)). That is exactly the "nothing left behind after `dispose()`" guarantee from system.md §7.5, scoped to a single box. Eloi needs about thirty lines that wrap `effect` so each disposer registers with the current box's owner. The platform `AbortSignal` (see the composition section below) covers the non-reactive half.

Scheduling is the area where the research most directly corrects the current design. **None of the signal frameworks use `requestAnimationFrame` for propagation.** Preact signals and Solid 1.x run effects synchronously when the outermost batch ends. Svelte 5 and Solid 2.0 flush in a microtask ([Svelte $effect docs](https://svelte.dev/docs/svelte/$effect); [InfoQ on Solid 2.0](https://www.infoq.com/news/2026/05/solidjs-2-async/)). React's scheduler is a min-heap of five priorities, driven through `MessageChannel` to avoid the 4 ms `setTimeout` clamp, and it exists only because VDOM diffing is unbounded work that must be time-sliced ([React Scheduler.js](https://raw.githubusercontent.com/facebook/react/main/packages/scheduler/src/forks/Scheduler.js)). Eloi's per-frame work is bounded by design, so system.md §7.3's single loop with read/evaluate/write phases is right. Its "priorities" plus `scheduler.postTask` yielding should stay a fixed phase order (input, then host, then layout, then decoration), not grow into lanes or time slicing. Svelte's newer batch code, with forks, speculative commits and pending-async counters ([svelte batch.js](https://raw.githubusercontent.com/sveltejs/svelte/main/packages/svelte/src/internal/client/reactivity/batch.js)), together with Solid 2.0's async-in-the-graph, show how fast schedulers grow once async enters the reactive graph. **Keep fonts, images and Supabase fetches in the load stage, outside the graph, and write their results into signals once they resolve.**

## Islands are Eloi's frame without the grid

An Astro island is a server-rendered region wrapped in a custom element. The element carries its module URL, serialized props, slot HTML and a trigger strategy, and a tiny loader upgrades each one independently ([astro-island.ts](https://raw.githubusercontent.com/withastro/astro/main/packages/astro/src/runtime/server/astro-island.ts)). Jason Miller's original framing applies directly: the static HTML is "a meaningful and immediately renderable representation", and each island is an isolated unit, so one island's performance problems do not spread ([Jason Miller](https://jasonformat.com/islands-architecture/)). That is Eloi's frame with the layout added. The compiled CSS grid decides where the islands are, and the static HTML and SVG in each opening is the fallback. Astro's trigger directives are each a few lines of platform code: `client:idle` uses `requestIdleCallback` with a load fallback, `client:visible` uses IntersectionObserver with `rootMargin`, and `client:media` uses `matchMedia` ([Astro directives](https://docs.astro.build/en/reference/directives-reference/)). Eloi should copy them as a per-box `when` field. Astro also isolates failures well. A failed island fires a cancelable `astro:hydration-error` and the rest of the page carries on. Eloi should do the same with an `eloi:box-error` event that leaves the static fallback in place.

Eloi does not need hydration, because it never re-renders server HTML. A box is either static, or its runtime takes over its own subtree, replacing or overlaying the fallback. Hydration mismatch therefore cannot happen. Layout shift cannot either, because box size comes from the frame grid and not from the runtime. Nested-island ordering, which accounts for much of the complexity in Astro's loader, does not apply, because frame openings are flat siblings or nested elevations with their own hosts. Qwik's resumability serializes listeners, component boundaries and subscriptions into HTML so that handler chunks download only when events fire ([Qwik: Resumable](https://qwik.dev/docs/concepts/resumable/)). It costs a closure-splitting compiler and strict serializability, and Qwik 2 reportedly grows the HTML payload ([DEV: Qwik 1 vs 2](https://dev.to/falselight/qwik-1-vs-2-quick-comparison-2f39)). The payoff disappears for boxes that need their full runtime the moment they become visible, which is every GPU box Eloi plans to host. The one idea worth taking is one delegated listener that lazily `import()`s a module named in a `data-*` attribute, and only for small interactive bits inside otherwise static boxes. Islands cannot share framework context, which is why Astro recommends a store of under 1 KB ([Astro: sharing state](https://docs.astro.build/en/recipes/sharing-state-islands/)). In Eloi the frame host plays that role by passing the same signal explicitly to both boxes.

Lit contributes a lifecycle discipline rather than a dependency. It is about 5 KB ([lit.dev](https://lit.dev/docs/)). Its reactive-controller protocol is small: `hostConnected`, `hostUpdate`, `hostUpdated` and `hostDisconnected` hooks, plus `addController` and `requestUpdate` on the host ([Lit controllers](https://lit.dev/docs/composition/controllers/)). Any object can act as a host, which is the relationship `<frame-elevation>` should have with its boxes. The frame owns the single ResizeObserver, IntersectionObserver and frame scheduler, and fans their results out. Lit's lifecycle docs carry a warning that matters for the city game: moved elements fire disconnect and then connect ([Lit lifecycle](https://lit.dev/docs/components/lifecycle/)). Box teardown should therefore be deferred a frame and cancelled if `isConnected` comes back true, so a DOM move never destroys a GPU context.

On styles, the research supports decision 6 in system.md (cascade layers by default) and sharpens it. `@layer` only orders precedence. It does not isolate. `@scope (root) to (limit)` gives one-directional "donut" scoping, so frame styles can stop at each opening, and **it became Baseline when Firefox 146 shipped in December 2025** ([web.dev, Dec 2025](https://web.dev/blog/web-platform-12-2025?hl=en); [MDN @scope](https://developer.mozilla.org/en-US/docs/Web/CSS/@scope)). Shadow DOM gives real two-way isolation, and Declarative Shadow DOM has been Baseline since August 2024, so it costs no JavaScript at first paint ([web.dev DSD](https://web.dev/articles/declarative-shadow-dom)). The cost is that theme CSS reaches in only through custom properties. ID-based ARIA references also cannot cross the boundary until "Reference Target" ships, and it was only at Intent to Ship in Chromium in June 2026 ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/eBx3sXIfJnw)). For a portfolio whose slots hold the site's own Tailwind-styled content, **the default should be light DOM, with frame chrome in `@layer eloi.frame` inside `@scope (frame-elevation) to ([data-slot])`**. Shadow DOM should be a per-box opt-in for foreign content.

## Layout engines agree: width goes down, height comes up, and the parent owns position

Every serious layout engine reduces to one per-axis negotiation, and Eloi's frame contract already picks the strictest version of it. Flutter's rule is "Constraints go down. Sizes go up. Parent sets position." A widget "can't know and doesn't decide its own position" ([Flutter: constraints](https://docs.flutter.dev/ui/layout/constraints)). Compose goes further and throws a runtime exception if a child is measured twice, with intrinsic queries as a separate side channel ([Compose intrinsics](https://developer.android.com/develop/ui/compose/layouts/intrinsic-measurements)). SwiftUI is the opposite extreme: the parent proposes a size, may probe the child several times, and must accept whatever size the child picks ([WWDC22](https://developer.apple.com/videos/play/wwdc2022/10056/)). Eloi's axis-typed expressions (frame-engine.md §4.1) are a static proof of the Compose discipline. An x-value that mentions a y-datum is rejected at load time, so there is exactly one pass per axis and no runtime check is needed.

Flutter's relayout boundary is the idea Eloi should adopt explicitly. In the Flutter source, a node is a boundary when `!parentUsesSize || sizedByParent || constraints.isTight` ([RenderObject.layout](https://api.flutter.dev/flutter/rendering/RenderObject/layout.html)). Changes inside a boundary never dirty its parent. In Eloi terms, frame-engine.md §4.3's *metric slots* and any fixed-aspect canvas box are boundaries: the frame fixes both axes, and content changes never reach the frame. *Content slots* have `parentUsesSize = true`: their measured height flows up into row tracks, track lengths and repeat counts. The box contract should declare this per box (`sizing: 'fixed' | 'hug'`). That one field decides whether a box gets `container-type: size` and `contain: size`, or `container-type: inline-size`, and whether the frame listens to its height at all. SwiftUI's `ViewThatFits` is a useful negative example. It chooses a variant by measuring whether the content fits, which is precisely the height-depends-on-variant-depends-on-height loop that frame-engine.md rules out with "variant choice never depends on content height". Eloi's room levels are a container query or Flutter's `LayoutBuilder`, not `ViewThatFits`. SwiftUI's `AnyLayout`, which switches layout algorithms while preserving view identity, states the matching rule for boxes: **a variant swap re-templates the grid but must never remount a box's runtime.**

Most of this is now native. Subgrid has been Baseline widely available since September 2023 and inherits parent track sizes and line names ([MDN subgrid](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_grid_layout/Subgrid)). Size container queries add containment specifically to prevent descendant-to-container loops ([MDN container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_containment/Container_size_and_style_queries)). Core anchor positioning became Baseline newly available with Firefox 147 in January 2026 ([web.dev, Jan 2026](https://web.dev/blog/web-platform-01-2026?hl=en)). The Houdini Layout API never shipped beyond a 2018 Chromium Intent to Implement ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/gVvtbIjE2J4/m/0KWy4Ew2CQAJ)). So frame-engine.md §4.2's plan ("compute in JS, emit CSS grid with datum line names") is the practical replacement, not a stopgap. Inside a box, `container-type: inline-size` plus `cqi` units let content adapt to the width the frame gave it with no JavaScript. Height flows up through `auto` grid rows, also with no JavaScript.

ResizeObserver's loop rule explains why JavaScript should not write heights. Notifications are delivered in rounds, and after each round only elements *deeper* than the shallowest one just delivered can be notified again. Shallower ones are deferred a frame with the "loop completed with undelivered notifications" error, which "only prevents user-agent lockup, not the infinite loop itself" ([MDN ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver); [CSSWG draft](https://drafts.csswg.org/resize-observer/)). A frame that writes to its slots is a downward write and resolves in the same frame. A slot that writes the frame's height is an upward write: it flashes a frame and logs an error. Eloi should read slot heights from observer entries, never from `offsetHeight`, use them only to redraw the absolutely positioned frame SVG, and leave the actual row heights to CSS.

For the later GPU hosts, the useful layout precedent is Taffy's two-level API. A high-level tree handles caching. A low-level trait lets a host keep its own tree and call the flex or grid algorithms per node, which is recommended "for embedding Taffy in a wider layout or UI system" ([docs.rs/taffy](https://docs.rs/taffy/latest/taffy/)). Yoga adds a `HasNewLayout` flag so the host re-applies only the subtrees that changed ([Yoga incremental layout](https://www.yogalayout.dev/docs/advanced/incremental-layout)). Eloi's layout planner should therefore be a pure `solveFrame(spec, width, measure) → { datums, boxRects, variant }`. The DOM backend compiles that to CSS. A map or regl box receives its rect only when its dirty flag is set. This costs nothing for the portfolio, because the planner has to exist anyway. It just has to avoid reaching into the DOM.

## GPU engines want the host to own size, clock and context

R3F is the strongest precedent for system.md's `MountOptions.clock`. Its `frameloop` prop is `always`, `demand` or `never`. In `demand` mode, `invalidate()` "merely requests a new frame" and acts as a coalescing dirty flag. In `never` mode the host drives ticks through `advance(timestamp)` ([R3F Canvas](https://r3f.docs.pmnd.rs/api/canvas); [R3F scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)). Its `gl` prop takes an async factory, which is how `WebGPURenderer` with `await renderer.init()` gets in. It also sets an ownership rule: R3F disposes renderers it created, and callers dispose ones they injected. MapLibre's custom layer interface shows the other side, a host that owns the WebGL context, the drawing-buffer size and the loop. Guests get `onAdd`/`prerender`/`render`/`onRemove` hooks with documented GL-state assumptions, and they request frames with `map.triggerRepaint()` instead of running their own rAF ([MapLibre CustomLayerInterface](https://maplibre.org/maplibre-gl-js/docs/API/interfaces/CustomLayerInterface/)). deck.gl's `MapboxOverlay` defaults to a separate stacked canvas. Interleaving into the shared context requires WebGL2 and gives up MSAA and pixel-ratio control ([deck.gl MapboxOverlay](https://deck.gl/docs/api-reference/mapbox/mapbox-overlay)). regl, isidex's core, is the easiest of all to slave to an external clock. `regl.frame(cb)` is a thin rAF wrapper with `cancel()`, and a host that runs its own loop "must call `regl.poll()`". `regl._refresh()` resyncs after anyone else touches the GL state ([regl API](https://raw.githubusercontent.com/regl-project/regl/main/API.md)).

The platform constraint that decides canvas strategy is the per-page WebGL context cap. Chrome warns "Too many active WebGL contexts. Oldest context will be lost", and **WebKit adopted the same limit of 16 that other browsers use** ([WebKit commit](https://webkit.googlesource.com/WebKit/+/70e10861eb2fbd9d0862fd8702874c25ae5d8bfd); [fingerprintjs PR](https://github.com/fingerprintjs/fingerprintjs/pull/484)). Apps that mount and unmount canvases hit it unless they call `WEBGL_lose_context.loseContext()` on teardown ([PlayCanvas forum](https://forum.playcanvas.com/t/too-many-active-webgl-contexts/13030)). drei's `<View>` avoids the cap by cutting one full-page canvas into DOM-tracked regions with `gl.scissor`, at the cost of per-frame `getBoundingClientRect` reads and a single shared renderer ([drei View](https://drei.docs.pmnd.rs/portals/view)). Eloi's GPU hosts each put *one* large box running a *different* engine on a page: a custom WebGL/WebGPU map in the city game, regl in isidex. So **per-box canvases are the right default, with explicit context loss on dispose**. A shared scissored canvas belongs only to a future gallery of many same-engine thumbnails.

Three more precedents set the shape of the GPU half of the contract. Crisp canvases need `ResizeObserver` with `box: 'device-pixel-content-box'`. Web.dev lists it as unsupported in Safari, so the fallback is CSS size times `devicePixelRatio` ([web.dev](https://web.dev/articles/device-pixel-content-box)). R3F clamps DPR to `[1, 2]` by default, which is worth copying for a large map box because fill cost grows with the square of DPR. OffscreenCanvas transfer has been Baseline since March 2023 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/transferControlToOffscreen)), and a worker-owned canvas cannot measure the DOM. So **size must be data the frame pushes, never something the runtime measures**, and that rule costs the portfolio nothing today. Device loss is part of both APIs (`webglcontextlost`; luma.gl's `device.lost` promise, with a suggestion to reload since recovery is hard) ([luma.gl Device](https://luma.gl/docs/api-reference/core/device)), so the contract needs a "lost/remount" channel. WebGPU is on by default in Chrome, Edge, Firefox (Windows and Apple Silicon macOS) and Safari 26 as of late 2025 ([web.dev](https://web.dev/blog/webgpu-supported-major-browsers)), but Android coverage is partial and Firefox Android had not shipped, so the map engine still needs a WebGL2 fallback behind an async factory.

The portfolio does not need any of this mechanism, but it should not shut any of it out. Two decisions keep it open at nearly zero cost. First, the frame scheduler should already have R3F's `demand` semantics: a coalescing `requestFrame()` and no rAF at all when nothing is dirty. That is system.md's "no work while idle" made structural. Second, box geometry should arrive as a pushed signal that carries `dpr`. Everything else, including `always`/`never` modes, `advance(t)`, device-pixel sizes, context-loss events and a MapLibre-style guest-layer hook inside the map engine, can wait for the city game.

## single-spa parcels, not Module Federation, are the composition model

single-spa's contract is small and directly reusable. Units export async `bootstrap` (run once), `mount` and `unmount`, and every lifecycle "must either return a `Promise` or be an `async function`" ([single-spa: building applications](http://single-spa.js.org/docs/building-applications/)). Its *parcels* are the close analogue of an Eloi box. They are mounted by code rather than by URL, have an optional `update(props)`, and when created through `mountParcel` they are tied to the parent's lifetime and unmount with it ([single-spa: parcels](http://single-spa.js.org/docs/parcels-overview/)). A unit that throws during any lifecycle is marked `SKIP_BECAUSE_BROKEN` and siloed while the others continue ([single-spa API](https://single-spa.js.org/docs/api/)). Eloi's existing `FrameHandle` already looks like a parcel (`set` is `update`, `dispose` is `unmount` plus `unload`). The missing piece is the same parcel shape one level down: the frame mounting boxes, owning their lifetimes, and isolating their failures.

Most of the rest of micro-frontend practice is aimed at problems a single developer does not have. Fowler's list of costs (duplicated dependencies, global CSS collisions, coupling through shared state, environment drift, operational overhead) is real ([martinfowler.com](https://martinfowler.com/articles/micro-frontends.html)), but for one person with one Vite toolchain only three matter: style leakage, leaked global runtime state, and two copies of the signals library creating two disconnected graphs. Module Federation 2.0 solves dependency duplication with a manifest, a runtime and singleton version negotiation ([module-federation.io](https://module-federation.io/guide/start/index.html)), all of which is wasted at this scale. Dynamic `import()` per box kind, plus at most one import map (Baseline since March 2023 ([MDN](https://developer.mozilla.org/docs/Web/HTML/Element/script/type/importmap))) to share `eloi` and `@preact/signals-core` across projects, covers it. Web Fragments gets "nothing left after destroy" by running each fragment's JavaScript in a hidden iframe realm ([Web Fragments: reframing](https://web-fragments.dev/documentation/reframing/)). Eloi can get most of that guarantee by contract instead: one `AbortSignal` per box that every listener, `fetch` and frame subscription is registered against, with DOM access confined to the box element. Fowler prefers explicit callbacks and data passed down from the container over implicit custom events. That matches decision 5 in system.md (`set()` backed by signals, an event bus only if needed) and argues for a typed `emit` rather than free-form DOM events.

Two platform APIs now change the shell design in frame-engine.md §12.5. The **Navigation API reached Baseline newly available in January 2026** (Firefox 147, Safari 26.2, Chrome since 102) ([web.dev](https://web.dev/blog/web-platform-01-2026)). It replaces the planned ~150-line History-API router's link interception and `popstate` handling with a single `navigate` event covering links, forms and back/forward. That event offers `intercept({ handler })`, built-in scroll and focus restoration, and an `event.signal` that aborts when a navigation is superseded ([Chrome docs](https://developer.chrome.com/docs/web-platform/navigation-api)). That signal can be passed straight into box loads. Because "newly available" leaves pre-2026 Safari and Firefox users for some time, keep a thin History fallback. Same-document View Transitions are Baseline since Firefox 144 ([web.dev](https://web.dev/blog/same-document-view-transitions-are-now-baseline-newly-available)). **Element-scoped transitions shipped in Chrome 147 in March 2026.** With them, `boxEl.startViewTransition()` pauses only that subtree, transitions with non-overlapping scopes run concurrently, and `view-transition-scope` keeps a box's internal names from colliding with the frame's ([Chrome blog](https://developer.chrome.com/blog/element-scoped-view-transitions); [Chrome docs](https://developer.chrome.com/docs/css-ui/view-transitions/element-scoped-view-transitions)). They are Chromium-only, so for a route change that swaps only the main box they are a progressive enhancement over a document transition that names only that box. Stable box ids (`view-transition-name: eloi-box-<id>`) are what let a route change work as a diff: boxes present in both frames are kept and updated, removed ones are disposed, and new ones are mounted.

## Conclusion: the box is a parcel with a relayout boundary

The research recasts Eloi's refined idea more than it extends it. What the docs currently describe as Eloi being a *guest* (mounted with a host's clock and scheduler) and what the user now describes as Eloi being a *host* (a frame whose boxes run their own runtimes) are the same contract applied at two levels. single-spa's parcels nest the same way, and R3F's `never` mode with `advance()` is what lets either side own the clock. The box contract is a combination of three precedents: a single-spa parcel for lifecycle and error isolation, a Flutter relayout boundary for the sizing declaration, and a MapLibre/R3F guest for the clock and size channels. Each of the three adds only a few fields. The non-obvious consequence is that the frame and its boxes should share **one** frame scheduler and **one** set of observers. That is what makes "no work while idle" true for the whole page, not just for the frame drawing.

The biggest risk the research identifies is borrowing a whole framework's model when one mechanism is enough. Every framework surveyed grew its complexity from one source: async inside the reactive graph (Svelte forks, Solid 2.0), unbounded diffing (React's scheduler), serialization of closures (Qwik), or cross-team version negotiation (Module Federation). None of those sources exists in a portfolio whose boxes are mostly static HTML. The contract below is sized for the portfolio, and its GPU half exists only as reserved names.

## Proposed box contract

The sketch connects to the existing `mount()`/`MountOptions`/`FrameHandle` in system.md §7.5 and to `<frame-elevation>` with `data-slot` openings in frame-engine.md §12.1. Fields marked *deferred* are reserved names with no portfolio implementation.

```ts
// ── Declared in the frame document; compiled at design stage into frame.css + plan.js ──
interface BoxSpec {
  id: string;                         // stable, from the document path; diff key + view-transition-name
  slot: string;                       // grid area from the plan (frame-engine.md §4.2)
  sizing: 'hug' | 'fixed';            // hug: exact width down, height flows up (parentUsesSize)
                                      // fixed: frame sets both axes → relayout boundary, container-type: size
  aspect?: string;                    // fixed boxes only, an expression on width inputs
  runtime?: string;                   // module specifier; absent ⇒ static HTML box, zero JS, no lifecycle
  when?: 'load' | 'idle' | 'visible' | 'interaction' | `media:${string}`;  // default 'visible'
  isolate?: 'scope' | 'shadow';       // default 'scope' (@layer + @scope donut); 'iframe' deferred
}

// ── What the frame gives a box runtime ──
interface BoxContext<I = unknown, O extends Record<string, unknown> = {}> {
  readonly id: string;
  readonly signal: AbortSignal;                 // aborted on dispose, route abort, or remount
  readonly geometry: ReadonlySignal<BoxGeometry>; // pushed by the frame's single ResizeObserver
  readonly visible: ReadonlySignal<boolean>;    // frame's single IntersectionObserver + visibilitychange
  readonly reducedMotion: ReadonlySignal<boolean>;
  readonly input: ReadonlySignal<I>;            // fed by FrameHandle.set / the router; replaces update()
  emit<K extends keyof O>(type: K, detail: O[K]): void;  // typed out-channel, bubbles to FrameHandle.on
  requestFrame(): void;                         // coalescing dirty flag (R3F invalidate / triggerRepaint)
  onFrame(fn: (t: number, dt: number) => void, phase?: 'read' | 'render'): () => void;
                                                // runs only after requestFrame; auto-removed on abort
  effect(fn: () => void | (() => void)): void;  // signals-core effect owned by this box (Solid createRoot)
  // deferred (GPU hosts): clockMode: 'demand' | 'always' | 'never'; onContextLost(cb); requestRemount()
}

interface BoxGeometry {
  inline: number; block: number;        // CSS px, fractional (contentBoxSize)
  dpr: number;                          // clamped by box policy
  room: number; variant: string;        // z = log_φ(size/sRef) and the frame's chosen variant
  // deferred: pixelInline, pixelBlock (device-pixel-content-box); local rect for solveFrame backends
}

// ── What a box runtime gives the frame ──
interface BoxRuntime<I = unknown, O extends Record<string, unknown> = {}> {
  mount(el: HTMLElement, ctx: BoxContext<I, O>): void | Promise<void>;  // async allowed (WebGPU init later)
  dispose?(): void | Promise<void>;     // after ctx.signal aborts; must release anything signal can't
                                        // (GPU: loseContext()/device.destroy() if the runtime created it)
}

// ── Additions to the existing FrameHandle (system.md §7.5) ──
interface FrameHandle {
  /* existing: set, signal, play, on('solved'|'variant'|'error'), dispose */
  box(id: string): { state: ReadonlySignal<'static' | 'loading' | 'live' | 'broken'>;
                     on(type: string, cb: (detail: unknown) => void): () => void };
}
```

Behavioural rules that go with the types:

| Rule | Precedent |
|---|---|
| A static box needs no lifecycle; a box with a runtime gets a `data-state` attribute for CSS hooks. | Enhance, Astro `ssr` attribute |
| `mount` and `dispose` are wrapped; a throw marks the box `broken`, keeps its fallback and emits `eloi:box-error`. | single-spa `SKIP_BECAUSE_BROKEN`, Astro hydration-error |
| Disposing the frame disposes boxes in reverse order; teardown is deferred a frame and cancelled if the element is reconnected. | single-spa `mountParcel`, Lit reconnect warning |
| Effects only mark dirty; one rAF runs read → evaluate → write, and no rAF is requested while nothing is dirty. | TC39 Watcher, R3F `demand`, system.md §7.3 |
| Variant swaps re-template the grid and never remount a box. | SwiftUI `AnyLayout` |
| Size is pushed, never measured by the runtime; JS never writes row heights. | MapLibre host-owned buffer, ResizeObserver depth rule |
| Box event listeners attach to the box element or to `ctx.signal`, never to `document`. | Vue Vapor delegation pitfall |
